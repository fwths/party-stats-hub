# Findings Registry

This document is the authoritative record of all audit findings.

The registry persists findings across audit runs and serves as the single source of truth for risk tracking, remediation status, regressions, accepted risks, and audit history.

All findings generated by audit agents must eventually be represented in this registry.

Findings are never deleted.

---

# Registry Purpose

The Find​​ings Registry exists to:

- Track findings across multiple audits
- Preserve audit history
- Prevent duplicate reporting
- Track remediation work
- Detect regressions
- Support release readiness reviews
- Provide risk visibility

---

# Registry Rules

## Rule 1: Findings Are Permanent

Once a finding receives an ID it remains in the registry forever.

Even after resolution.

---

## Rule 2: IDs Are Never Reused

A finding ID may only refer to one issue.

Examples:

```text
DND-001
ARC-004
CMP-010
COD-021
```

IDs must never be recycled.

---

## Rule 3: Regressions Reuse Existing IDs

If a previously resolved finding returns:

Do not create a new ID.

Update the existing registry entry.

Example:

```text
DND-004

Status: Open
Lifecycle: Regressed
```

---

## Rule 4: Official Findings Only

Only official findings belong in the registry.

Observations do not belong in the registry.

Ownership disputes do not belong in the registry.

Unverified concerns do not belong in the registry.

---

## Rule 5: One Owner Per Finding

Every finding must have exactly one owner.

Ownership is governed by:

```text
PROJECT_CONTEXT.md
```

# Field Definitions

## id

Unique identifier.

Example:

```text
DND-004
```

---

## title

Human-readable summary.

Example:

```text
Expertise applies proficiency twice
```

---

## owner

Official owning agent.

Examples:

```text
Architecture & Data Model Agent

D&D Domain Agent

Campaign & Collaboration Agent

Code Quality & Reliability Agent
```

---

## severity

Allowed values:

```text
Critical
High
Medium
Low
Info
```

Severity is governed by:

```text
SEVERITY_MATRIX.md
```

---

## confidence

Allowed values:

```text
High
Medium
Low
```

---

## status

Allowed values:

```text
Open
Accepted
In Progress
Resolved
Rejected
```

---

## lifecycle

Allowed values:

```text
New
Existing
Resolved
Regressed
```

---

## first_detected

Date first discovered.

Format:

```text
YYYY-MM-DD
```

---

## last_reviewed

Most recent audit review.

Format:

```text
YYYY-MM-DD
```

---

## resolution_commit

Commit SHA that resolved the issue.

Optional.

Examples:

```text
abc1234
```

```text
n/a
```

---

## regression_count

Number of times the issue has returned.

Example:

```text
0
```

```text
2
```

---

## category

Finding category.

Examples:

```text
Rules Engine
Character Calculation
Architecture
Campaign Management
Security
Reliability
Performance
```

---

## location

Repository location.

Examples:

```yaml
location:
  file: src/rules/CharacterCalculator.ts
  line: 284
```

or

```yaml
location:
  file: Architecture
```

---

## description

Problem explanation.

---

## impact

Business, user, gameplay, technical, or operational impact.

---

## recommendation

Preferred remediation.

---

## notes

Optional context.

# Finding Lifecycle

## New

Definition:

Finding discovered for the first time.

Example:

```yaml
status: Open
lifecycle: New
```

---

## Existing

Definition:

Known issue that remains unresolved.

Example:

```yaml
status: Open
lifecycle: Existing
```

---

## In Progress

Definition:

Work has started.

Example:

```yaml
status: In Progress
lifecycle: Existing
```

---

## Resolved

Definition:

Issue fixed and validated.

Example:

```yaml
status: Resolved
lifecycle: Resolved
```

---

## Regressed

Definition:

Previously resolved issue has returned.

Example:

```yaml
status: Open
lifecycle: Regressed
```

---

## Accepted

Definition:

Known issue intentionally accepted.

Example:

```yaml
status: Accepted
lifecycle: Existing
```

---

## Rejected

Definition:

Finding determined to be invalid.

Example:

```yaml
status: Rejected
lifecycle: Existing
```

# Release Readiness Rules

A release should not proceed if:

- Open Critical findings exist
- Regressed Critical findings exist
- Character integrity risks remain unresolved
- Campaign integrity risks remain unresolved

The Repository Director is responsible for reporting release blockers.

---

# Success Criteria

A healthy registry demonstrates:

- Clear ownership
- Accurate severity
- Traceable history
- Low regression count
- Consistent remediation progress

The registry should provide a complete historical record of repository health over time.
